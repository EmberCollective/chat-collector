# 架构审查与试运行验收

本轮以 [B01–B13 架构契约](architecture.md) 为准。审查先复现失败场景，再修复并补回归；测试通过范围与真实账户验证分开记录。最终源码和包版本以 `release-manifest.json` 为准，半天试运行之后仍由用户决定是否合并。

## 已确认问题与修复

| 问题 | 修复及验收重点 |
|---|---|
| 微信部分分片刷新失败后，显式重放仍可读混合库组 | 来源记录持久未完成状态，未完整发布的版本拒绝查询；重试复用已提交分片，原生回归验证其写入量为零 |
| 采集水位绑定筛选状态，同一来源无法供多个消费者使用 | 发布记录归来源，消费者各自保留筛选断点；兼容读取旧记录 |
| 无规则、坏规则、筛选状态损坏或导出失败会阻止采集 | 组合入口先执行独立采集，再筛选；节流依据采集时间，缺水位时立即刷新 |
| 迟到行改变连续性，重放却不发布修订 | 将连续性事实纳入语义摘要；旧摘要用索引核对后迁移，3000 条旧事件验证零重发 |
| 附件高级适配实现仍归收集包 | 移入兼容层，旧导入转发到同一实现，继续复用原生引擎 |
| 同内容异名附件丢失第二名称 | 保留独立附件引用；内容缓存共享；验证材料导出、资源组包及渠道交付，兼容旧文件回执 |
| 同批多个会话无法更新同一已有任务 | 允许分会话提交一致的最终字段，分别保留证据；冲突内容可由模型修正，外部内容变更仍拒绝覆盖 |
| 旧卡片操作冲突后永久阻止新卡和提醒 | 只有待执行反馈阻塞；冲突/失败终态允许同步最新正式状态，旧请求仍不能覆盖新修订 |
| 自定义飞书目标 ID 无法自动监听 | 按启用目标选择应用，兼容接管旧监听命令；同应用多群共用连接，多应用明确报告限制 |
| 早报重试仍含已完成任务 | 发送前重建明确未送达的早报，同时更新飞书缓存；已发卡但附件失败时更新原卡，不重复发送 |
| 单个长来源归档损坏阻塞整轮投递 | 资源级降级，损坏内容不得上传，其他任务继续投递 |
| 调度状态读取被写入阻塞，报警仅有异常类型 | 状态库改用 WAL，结构只迁移一次；保留安全 SQLite 错误码和项目内位置，不保留 SQL、正文或密钥 |

运行时更改为多个飞书应用时，监听监督器保留正在运行的连接并报告配置错误；修正配置后解除错误。自动监听仍只管理一个应用，多个群可以属于同一应用。多个应用需要显式独立部署监听器。

## 架构逐项核对

| 契约 | 实现与证据 |
|---|---|
| B01 单项目 | 同一个 Python 项目与现有 Pi Node 运行时，没有新增微服务或消息中间件 |
| B02 独立收集 | 来源共享采集水位；没有规则和筛选故障都不阻断采集；跨分片未发布版本拒绝读取 |
| B03 SQL 适配 | 平台解析、统一临时 SQLite、参数绑定与执行归 `providers`；`selection` 只编排规则并合并命中 |
| B04 附件归兼容层 | Pi 工具调用公开内容接口；高级定位、解码、解析和归档归提供方 |
| B05 AI 边界 | 只有 Pi 进行语义判断，收集、SQL、持久化、调度和渠道不用 AI |
| B06 标准输入 | 人物、群、来源由提供方补齐；只投影当前上下文涉及的人物，处理层不补查平台私有库 |
| B07 唯一待办库 | 所有正式修改通过待办服务；消息层消费变更流，反馈不直接写任务表 |
| B08 编排与渠道 | 消息层决定时间、目标、重试与去重；渠道负责呈现、上传、发送和回调校验 |
| B09 人工控制 | 人工完成、恢复、改级在后续 AI 更新中保留；完成后停止提醒 |
| B10 规则并集 | 同窗口同快照执行所有规则，合并去重，保留真实命中规则和上下文 |
| B11 Pi 原生机制 | 保留原生循环、压缩和重试；附件初始只提供索引，按需读取 |
| B12 可选面板 | 独立后台不依赖浏览器；核心不反向依赖调试台或安装器 |
| B13 迁移保留 | 保留原账号配置、明文库、断点、任务身份及回执；旧去重记录按需兼容，旧文件回执继续识别 |

## 真实账户检查

复用现有微信、QQ、模型与飞书配置；采集输出、筛选断点和模型写入留在隔离测试目录。正式待办仅用于只读查重。合成外部测试与真实任务卡片的测试副本不会更改正式任务。

| 路径 | 本轮证据与边界 |
|---|---|
| 微信数据库 | 首次基线约 9 秒；增量实测约 1–4 秒，5 个数据库验证通过 |
| QQ 数据库 | 首次基线约 123 秒；不同变化量的增量约 10–19 秒，只解密变化页并同步相关行 |
| SQL 与去重 | 最近 6 小时命中微信 29 条、QQ 11 条；同时保留 context、mentions-all、files 命中；同窗口重放零新增 |
| 真实模型 | 40 条消息组成 4 个上下文组；实际使用查重、附件读取、提交工具并保存待办；没有新增消息时零处理组 |
| 人工优先级 | 查重命中已有事项时保留其人工 P1 设置，未被模型重新覆盖 |
| 图片 | 微信按需准备图片和 QQ 已归档图片读取成功 |
| 文档 | 抽查历史 PDF、DOCX、DOC 时本地源文件缺失，工具明确返回不可用；不能据此宣称这些真实附件读取成功 |
| 飞书投递 | 实际发送测试待办，并实际更新远端卡片为已完成；重复运行没有重复发送 |
| 操作回写 | 本地模拟渠道回调完成了校验、入队、正式测试库更新和远端卡片刷新，约 3.8 秒；这不等于真实点击的长连接验收 |
| 长连接 | 测试监听曾两次握手超时，普通 API 正常。进程运行不等于连接成功，最终试运行需核对实际点击回执 |

这些耗时来自本机与当前数据量，不是性能上限。QQ 仍需捕获并验证源快照，不能把“只解密变化页”解释为整个过程耗时与数据库大小完全无关。

## 未覆盖与剩余限制

- 跨分片失败期间保留每个已验证库，但没有上一整组的独立副本；该组会暂停供查询，下一轮采集完成后恢复。已经发布的事件和待办继续处理。
- 任意旧时间消息的新增或修改不会自动触发历史全库扫描，需要显式时间重放；重放已能修正连续性变化。
- Notion 当前为数据源页面单向同步。Notion Calendar 原生接入及修改回流未完成，现有配置也未启用；不能当作已验证渠道。
- 自动状态的 WAL 备份使用 SQLite backup API；复制单独 `.db` 可能遗漏最近提交。
- 真实模型输出有语义误判可能，结构和来源校验不能代替业务准确率评估。
- 本轮复用已安装依赖与已有账号，不代表全新机器首次取钥、安装向导、重启登录或所有附件格式已经验收。
- 原生 Code Review / Security Review 尚未配置。独立 Agent 审查和本地测试不代替它们；本轮不合并主分支。

## 试运行部署要求

1. 保留原工作区、配置与数据；固定候选提交并构建带哈希清单的运行包。
2. 停止旧后台前，记录面板定时开关、任务状态及启动项；等待正在执行的任务完成，不中断解密事务。
3. 备份正式 SQLite 状态库与配置；候选继续使用这些相同账号和数据，禁止重新采集全量或重放历史模型任务。
4. 将原本由面板运行的已启用采集任务迁到独立调度，保留间隔，停止旧面板重复调度。
5. 启动候选后台和面板，核对真实加载路径、版本、任务状态与回调；更新原登录启动入口，防止新旧实例同时运行。
6. 半天试运行后由用户决定合并；发现故障先保存安全诊断，不以“期间没遇到”代替已知失败场景的回归测试。
