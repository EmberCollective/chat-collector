# 许可与再分发

本文回答当前仓库适合使用什么许可证、为何暂未添加根 `LICENSE`，以及把 MIT 作为目标时需要先解决什么。事实基线见 [第三方来源与许可](../../THIRD_PARTY_NOTICES.md) 与 [来源记录](../../third_party/provenance.json)。本文不是法律意见。

## 结论

**推荐目标：项目自有代码使用 MIT。当前状态：暂不添加根 MIT 许可证。**

MIT 适合希望降低采用门槛、允许商业使用和二次开发的项目。但本仓库当前包含无明确许可证的微信代码与 `wx_key`、GPLv3 的 QQ 协议解析代码，以及 AGPLv3／商业双许可的 PyMuPDF。只要这些材料仍在同一公开分发物中，就不能把整个仓库或安装包准确描述为“MIT 项目”，也不能用一份根 `LICENSE` 覆盖第三方代码。

当前更准确的描述是：**公开可见的实验性源码预览，项目级再分发许可尚未完成。** “公开可见”“可 fork”“能下载 ZIP”都不等于已经授予复制、修改或再分发权。

## 当前阻塞

| 材料 | 已确认约束 | 对 MIT 的影响 |
| --- | --- | --- |
| 微信提取代码 | 固定上游版本未找到覆盖相关文件的项目许可证 | 未取得明确授权或替换前，不能把包含这些文件的整体分发标为 MIT |
| `wx_key 2.0.1` wheel | wheel 与对应源仓库标签均未找到明确许可证 | 需要核实授权链、取得许可或更换组件 |
| QQ `c2c_40800` 协议解析 | 上游为 GPLv3 | MIT 不能覆盖 GPLv3 代码；组合分发义务需解决 |
| PyMuPDF 2.1 | AGPLv3 或 Artifex 商业许可 | 未取得商业许可或替换时，不能忽略 AGPLv3 分发义务 |
| Pi、TypeBox、QQ 扫描器等 | MIT | 可保留 MIT，但仍须保留原版权与许可文本 |

把 GPL/AGPL 目录单独放、加免责声明或附上本文，都不能自行消除相应义务。反过来，保留 MIT 的 Pi 或扫描器，也不会让整个组合变成 MIT。

## 可行路线

### 路线 A：清理阻塞后采用 MIT（推荐）

适合希望长期公开维护、接受第三方集成和商业使用的项目。顺序如下：

1. **确认权利归属。** 核实项目自有代码、贡献和资产的权利人；确认没有在 MIT 之外单独承诺过其他授权。
2. **解决微信代码与取钥组件。** 取得权利人的书面许可，或替换为 MIT/BSD/Apache 等授权明确的实现。仅修改文件名、重写少量代码或只发布二进制都不自动改变许可。
3. **解决 QQ 协议解析器。** 优先寻找并采用许可明确的独立实现；若继续使用 GPLv3 代码，则不能把它直接改标成 MIT。替换时保留协议行为测试和来源记录。
4. **解决 PyMuPDF。** 使用许可兼容的 PDF 实现替换，或取得 Artifex 商业许可。仅把调用放到独立进程或网络服务中，也不能在未核实的情况下假定 copyleft 义务消失。
5. **完成打包与通知。** 随源码和实际二进制包保留 `THIRD_PARTY_NOTICES.md`、`third_party/licenses/`、版权声明和必要源码；检查实际依赖树，而不只看顶层包。
6. **最后再添加根许可证。** 上述事项完成后添加标准 MIT `LICENSE`。根许可证只覆盖有权许可的项目代码；第三方材料继续按其自身许可处理。

### 路线 B：接受 GPLv3/AGPLv3 约束

如果决定保留 copyleft 组件，分发方式、源码提供、修改说明、网络使用等义务需要逐项判断，并由熟悉相关许可证的人确认。在当前仍有无明确许可的微信组件时，选择 GPLv3 也不能修复这些组件的授权缺口。

这条路可以实现合规的 copyleft 项目，但不再是 MIT，也不能把整个产物宣传为宽松许可。除非有明确的 copyleft 产品目标，否则不推荐作为当前默认路线。

### 路线 C：按文件混合许可

理论上可以只给项目自有文件加 MIT，并在每个 GPL/AGPL/第三方文件旁保留其原许可。但在本仓库当前状态下，这仍不能解决无许可证组件和组合分发问题，且识别与维护成本高。**不建议把“混合标注”当作绕过 copyleft 的办法。**

## 发布门禁

- 没有完成整体授权判断时，不添加根 MIT `LICENSE`，不在 README、Release 或安装器中写“MIT”“开源可自由再分发”。
- 每个实际发布包都包含第三方版权、许可证、NOTICE 和来源记录；缺一项就停止发布并修正打包清单。
- 依赖升级、裁剪或换包后重新核对许可，不能沿用旧版本的结论。
- 公开发布、商业分发或托管服务前，保存授权证据和对应源码版本；无法确认时缩小分发范围。
- 发现凭据或个人信息进入包或仓库时，优先按泄露处理并轮换，不以删除提交代替处置。

## 何时可以宣布 MIT

只有同时满足以下条件，才建议在 README 和发布页正式写“MIT”：

- 根 `LICENSE` 是标准 MIT 文本，日期和版权人准确。
- 所有项目自有代码、资产和贡献均已确认有权按 MIT 发布。
- 微信提取、`wx_key`、QQ 协议解析和 PyMuPDF 的阻塞均已取得授权、替换或完成兼容处理。
- 实际发布包保留全部第三方许可材料，且没有无许可证文件。
- 对外说明清楚：MIT 只覆盖项目有权授权的部分，第三方材料仍适用各自条款。

在完成这些条件之前，最稳妥的建议是继续保持“实验性本地预览、项目级许可证待定”，而不是选一个看起来简单的许可证标签。

> 涉及公开发行、商业授权或 copyleft 合规时，请让专业法律顾问审阅实际材料与分发方式。
