## 本轮完整首页测量（2026-11-15）

结论：已经找到可复现的无用等待——**首页被隐藏的 Pi 页面初始化阻塞，连续两次遍历历史并解析任务结果，之后才请求概览。** 先删这条等待链，再处理共享缓存与变化更新。SQL 索引有优化空间，但无法解决目录和 JSON 的重复读取。

本轮从浏览器导航开始，直到问题区、四项核心指标、成功率图、系统服务列表、资源占比图及来源表、采集表现表、刷新时间均有实际数据与 DOM，再等待两次绘制帧；不是只等 API 或骨架屏，也没有使用会被周期轮询干扰的 `networkidle`。检查间隔 100 毫秒，完成时点有约 0–100 毫秒的量化误差。

这是桌面 1440×1000 的两次无头 Chromium 检查，**没有复现用户现场完整 6000 毫秒，也没有据此声称现场只需两秒**。没有重启服务、清空系统文件缓存或覆盖用户的显示环境；两次样本不能计算可信 P95。DOM 加两帧是内部可用性判据，仍需与用户实际浏览器对齐。

### 完成前在等待什么

检查真实候选 `.runtime/candidates/eb117425` 与工作区的 `app.js`、`overview.js`、`workflow.js`、`automation.js`、`overview.py`、`workflow.py`、`storage_metrics.py`，规范化换行后内容一致。

```mermaid
flowchart LR
    A[会话与来源配置] --> B[隐藏的处理模块]
    B --> C[Pi 运行列表：完整扫描]
    C --> D[首次选择运行：再次扫描]
    D --> E[读取工作流事件]
    E --> F[请求并绘制首页概览]
```

| 首次检查的步骤 | 相对导航的开始 | 耗时 | 首页必需的前置条件 |
|---|---:|---:|---|
| Pi 运行列表第一次请求 | 216 ms | 825 ms | 否 |
| Pi 运行列表第二次请求 | 1042 ms | 795 ms | 否，而且重复 |
| 选中运行的工作流事件 | 1839 ms | 9 ms | 否 |
| 首页概览请求 | 1850 ms | 714 ms | 是 |
| 必需区域就绪并经过绘制帧 | — | 总计 2683 ms | 完成点 |

刷新仍先等两次 Pi 列表：857 + 833 毫秒；概览到 1857 毫秒才发出，本次接口仅 103 毫秒，完整完成点为 2010 毫秒。当前约 1.6 秒的历史扫描可以从首页关键路径移出，但最终提速多少仍须改后测量，不能直接相减承诺。

**目录解析的具体浪费：** `tools/console/workflow.py::runs` 对所有候选先调用 `read_run_metadata`，读取并解析 `job.json` 和完整 `result.json`，之后才判断是不是处理模块的 Pi 运行。列表只需要轻量信息，却支付了不相关任务结果的成本。本次只统计文件大小：控制台 253 个候选目录，元数据约 63 KB，结果文件逻辑大小合计 17.54 MB；初次两遍列表有潜在重复解析约 35 MB 结果 JSON 的工作。这里不是 Windows 实测物理盘读取字节：系统缓存、可读性与筛选会影响真实 I/O。

每次首页有 24 个 API 请求，其中会话 6 次、来源目录 2 次、Pi 列表 2 次。会话和目录应共用读取；重复会话本次较快，优先级低于两遍 Pi 扫描。

两次静态资源请求约 4–18 毫秒，未观察到持续至少 50 毫秒的主线程长任务。本轮主要等待在取数链路，而不是已证明的绘制瓶颈；其他设备和现场冷启动仍不能排除。中间件对响应统一设置 `Cache-Control: no-store`，刷新会重取静态资源，但这两次不足几十毫秒，不是首要优化点。**认证 API 保持禁止浏览器持久缓存，提速不应放宽它；共享缓存放在本机服务端。**

## 数据从哪里来

| 显示内容 | 实际来源 |
|---|---|
| 成功率、采集条数、平均/P95、后台执行记录 | 自动化 SQLite 的 `runs`、`run_attempts`，叠加控制台任务目录的 `job.json`、采集 `result.json` |
| 当前服务、调度、下次执行 | 自动化状态库与已核验的进程状态；概览 `jobs[].next_run` 已有字段 |
| 待办积压、投递及回写问题 | 处理与消息模块的 SQLite 状态及队列统计 |
| 消息贡献与存储占比 | 已记录的入库变更计数；配置范围内文件逻辑大小。目录盘点已有服务端 60 秒缓存及预算 |
| Pi 运行目录及工作流详情 | 各批次元数据文件、`pi-workflow.jsonl`；详情是结构化事件，原始文本日志用于下钻排错 |
| CPU、机械硬盘实时负载 | 目前没有接入，静态稿数值全部为合成示例 |

因此没有一个 SQL 索引能同时解决数据库查询、目录遍历、JSON 解析、串行请求和页面绘制。

## 当前证据

- 首页初始化 `tools/console/static/app.js::init` 顺序等待来源配置、状态、处理模块和 Pi 工作流，最后才 `initOverview`。概览会等待隐藏页面的准备工作。
- `initWorkflow → refreshWorkflow → loadWorkflowRuns` 后，首次选中工作流又调用 `selectWorkflow → loadWorkflowRuns`，相同目录连续读取两次。`tools/console/workflow.py::runs` 每次遍历历史目录并读取元数据，再排序分页。
- 一次真实浏览器只读请求记录中，两次工作流列表请求约 810 / 828 毫秒；概览约在 1884 毫秒才发起，该次请求约 1743 毫秒。另一次热访问概览响应约在 2005 毫秒到达。**这些仅是取数链路，不是完整主页显示时间；没有将任何一次局部读数当成 6000 毫秒全链路的复现。**
- 单独读取 `/api/overview?hours=24` 约 277 毫秒，`/api/operations/status` 约 42 毫秒；受服务缓存、系统文件缓存与并发影响，不能推出冷启动或整页一定很快。
- 概览每次请求仍重新读取控制台历史文件、自动化历史并聚合；自动化统计对每条轮次单独查询尝试次数，存在重复小查询。文件大小统计已有缓存，但整个概览和 Pi 目录没有对应共享结果缓存。
- 隐藏页的自动化状态每 5 秒请求，旧来源状态每 3 秒请求；初次打开多个脚本分别读取会话。浏览器刷新重复这套准备工作。

数据库只读查询计划：`runs` 已有主键和 `runs_started(started_at DESC)`；`run_attempts` 已有 `(run_id, number)` 主键索引。按模块查最近轮次目前扫描时间索引，且有末项临时排序；上一轮 15 条采集记录查询约 0.43 毫秒。最新读取总保留轮次约 2047 条，投递/回写各约 1000 条，数量随真实后台正常运行变化。尝试次数查询使用现有主键前缀索引。**有复合索引优化空间，但证据不支持将现有 6 秒主要归因于缺索引。**

本轮仅在**内存副本**复制轮次 ID、模块和时间，不复制结果正文；验证增加 `runs(module, started_at)` 后，原来的 `SCAN runs USING INDEX runs_started` 加临时排序，变为 `SEARCH runs USING INDEX runs_module_started (module=?)`。没有改真实数据库，也未测真实写入开销。索引可以作为后续小优化，但不能缓存 JSON 文件或解除浏览器的前置等待。

## 拟实施顺序

1. **先让当前页完成。** 会话和来源目录共用一次读取后优先加载概览；处理配置、Pi、SQL 编辑及自动化表单在进入相应页面时初始化。删除重复的 Pi 列表读取；列表先以轻量元数据判断模块/操作，再读取确有需要的状态摘要，避免不相关的大结果 JSON、隐藏页渲染成为首页前置等待。保留筛选、详情文件校验、冲突检查、分页与未保存编辑语义。
2. **服务启动后异步预热一次。** 建立有大小上限的历史元数据索引和首页汇总缓存；不阻塞服务启动，不靠第一次打开网页触发全量扫描。缓存由服务端共享，浏览器刷新或多窗口命中同一份结果，不复制聊天正文或 Pi 上下文。
3. **按变化更新，不按刷新重扫。** 复用已结束批次的元数据，只重读新增/变化/正在执行的记录；SQLite 的状态变化、配置版本和文件变动触发失效。先将尝试计数改为批量聚合，避免逐轮 SQL。多请求只允许一个重建者，其余使用现有快照，不在机械盘上并发重复扫描。
4. **把时效分开。** 当前页可见时，轻量服务/当前任务/错误与队列状态约 3–5 秒；历史质量与成功率约 15–30 秒共享更新；文件空间保留已有 60 秒缓存。仅对可见页轮询，隐藏暂停。保存、重试、恢复等已完成的操作使相关缓存失效并重新读取实际结果，不乐观伪报成功。
5. **缓存要标时间。** 沿用已有响应字段，尽量仅补充可选的分项采样时间/缓存状态；旧数据与实时状态分别标记。重建失败时保留带时间的旧数据并显示过期；没有快照时显示准备中，不补 0 或假正常。页面刷新不再触发无条件重建。
6. **索引按结果决定。** 在临时副本比较按模块与时间的复合索引，例如 `runs(module, started_at)`，与现有索引的查询计划和读写成本；仅在有收益时加这一个索引。保持 `run_attempts` 现有主键索引，不向所有表盲目加索引，不修改业务结果契约。
7. **最后接入轻量负载探针。** 与上述历史扫描分开；每 5 秒仅前台采样、共享计数器、最近 60 秒内存，不落库或持续追栈。模块共用进程部分标共享，不能以更高开销换取没有证据的精确归属。

缓存失效不能只比较 SQLite 主文件修改时间：当前使用 WAL，未合并的变更可能还在 WAL 中。实施时使用可验证的数据库变化信号和文件版本，活跃任务与已结束历史分别处理。没有查看者时不维持高频历史扫描；缓存只保留展示摘要，不复制完整任务或 Pi 正文。启动预热分批执行，不抢占正常采集；认证 API 的浏览器 `no-store` 保留不变。

验收使用**完整主页**，分别记录服务冷启动、服务已运行首次打开、再次打开、浏览器刷新和多窗口请求。计时覆盖首个页面请求至主页必需数据已呈现并完成绘制，同时记录请求瀑布和主线程长任务；不以 API 返回、骨架屏或加载事件代替完成。建议目标：热刷新完整主页 P95 不超过 1 秒；预热前首次显示以正确的准备状态先出现，完整显示时间单独报告，目标须用同一台机器实测，不预先承诺。

同时比较优化前后的后台 CPU、机械盘读取量、缓存内存与探针耗时；确认没有重复重建、隐藏页轮询、新增外部请求或业务触发。所有改动在用户审批后实施；当前静态稿与本方案不影响正在运行的采集、处理和投递。

未验证：服务冷启动、用户现场 6000 毫秒的全部时间、探针真实开销、索引在真实写入中的代价。本轮两次只读检查证明了重复取数和前置等待，不能冒充已经优化完成。
