# 行动与投递：逐项投递计划与每日早报

打开 [已批准的 HTML 参考稿](index.html)。本稿沿用拾序品牌、Logo、灰绿布局和字体，包含两个同级视图：待办与投递、每日早报。用户已批准迁移，真实实现与验证边界见 [实现验收](IMPLEMENTATION.md)；HTML 仍保留合成数据供对照。

所有待办、来源、目标、投递记录和服务状态均为合成数据。演示时刻固定为 **2026-11-15 17:00，Asia/Shanghai**；倒计时不随真实时钟走动。HTML 内联样式、脚本和原 Logo，可双击打开，无外部依赖或网络请求。侧栏链接回已有的离线设计稿。

## 本轮设计选择

- 每行代表一条**处理后的待办**，关联多条原文。一条聊天不必等于一个行动，也不等于一次投递；不把原始采集库的消息条数当成待投递数量。
- 主列表显示截止时间、下一次预计投递的具体时间、还需多久和投递原因。详情分别列出每个目标的状态、计划及最近回执；普通间隔按该目标自己的成功通知时间计算。
- 未知结果、反馈待回写明确显示阻塞原因，不编造倒计时。同一待办某个目标阻塞时，其他目标的计划仍可查看。纯同步目标显示“等待内容变更”，不误报成下一轮重复提醒。
- “每日早报”按日期、目标预览已知通知安排，显示预计开始时刻及补发窗口；逐项展示当日提醒时间，并解释其余待办为何未纳入。不增加无助于判断的统计卡片或新的调度入口。
- 计划与已排队、送达回执分开表达。仅日期截止标注按规则补足；未来早报内容是当前快照的预估，不冒充已生成的投递包。早报正文的布局为预览设计，实际外部渠道的呈现由适配器决定。

## 已核对的当前规则

依据 [消息层排队实现](../../../messaging/core.py)、[截止节点与早报实现](../../../messaging/notifications.py)、[权威调度契约](../../information/dispatch/contract.md)。本机配置的核对值如下，**不是新安装模板的默认启用状态**：

| 机制 | 当前本机配置 / 实现行为 |
| --- | --- |
| 首次通知 | P0–P4 均开启；处理后的有效待办被消息层接收后，于后台下一轮检查安排通知；不是每条原始聊天入库即发送 |
| 内容修订 | 仍会更新；不需要等到下个截止节点 |
| 截止提醒 | 已开启；按优先级的提前节点及截止时提醒，具体数组见草稿“查看当前投递规则” |
| 无截止日期 | 使用既有普通间隔；与截止提醒二选一 |
| 每日早报 | 已开启，上海时间 08:00，补发窗口 360 分钟，即当日 14:00 前；模板默认关闭，契约中示例补发窗口为 60 分钟 |
| 后台检查 | 本机自动化投递任务每 5 秒；独立消息服务的配置检查间隔另为 60 秒，不能混为同一个执行入口 |

早报汇总**生成时已知、当天有通知安排的未结束待办**，不等于全库待办或当天到期待办。消息层按各目标分别组织截止节点、已知首次通知、延后恢复及普通间隔；反馈阻塞项不纳入。Notion / 纯同步目标不额外接收早报。当前早报实现没有单独按“某目标有未知回执”过滤全部相关任务；未来展示和改动应据实际调度语义核对，不据草稿自行修改发送规则。

示例覆盖首次通知、截止节点、普通间隔、延后、单目标结果未知、全部目标反馈待回写、仅日期截止和已完成。次日早报包含 4 项；切到后天仅保留已知的普通间隔事项。个人提醒的上次成功时间不同，因此早报中的间隔提醒为 10:00，项目群为 09:00。

## 数据与迁移边界

静态稿的 `demo` 数据仅用于评审，节点为显式样例。真实实现使用消息层只读 `schedule`、`digest` 和单项详情接口；截止/间隔计划与早报内容复用实际消息层函数，前端不复制静态预览的调度逻辑。来源与目标按数据描述，不能靠前端平台名称判断规则。

静态 HTML 不执行真实查询、导入、材料归档、模型处理、反馈恢复和外部投递。正式页面保留显式材料导入、下载、任务完成/恢复/延后和投递恢复入口；查询计划本身不触发这些写入。
