## 审批重点

1. 六个目标入口是否清楚：运行概览、信息源调试、待办处理、行动与投递、运行记录、设置。
2. 采集页是否便于工作：左侧条件，中间消息，右侧来源详情；条件和结果各自滚动，预览按钮固定在条件区底部。窄屏点击消息使用详情对话框。
3. 操作范围是否易懂：只读预览、正式采集、历史重放、独立调试处理、向外投递分别说明结果。
4. 品牌绿、中文系统字体、信息密度与间距是否合适。
5. Pi 工作流是否足以追踪每轮上下文、模型可见输出、工具参数 / 返回、压缩 / 重试和最终保存结果。

可以切换信息源、搜索示例消息、筛选附件、编辑预览注册表、试验非法时间、取消预览、查看任务来源，以及演示投递未知状态的恢复流程。设置中可从示例渠道目录添加默认关闭的目标实例。待办处理中的“Pi 工作流”可切换完成、执行中与失败场景，筛选和展开事件；也可直接打开 `index.html#pi-workflow`。重新打开或刷新会恢复默认示例。

## 新信息源与渠道的设计约束

页面中的微信、QQ、外部来源和渠道名称只属于演示目录。选择器、设置表单、能力入口和目标提示由目录数据生成；不在渲染与操作分发中根据品牌名称写分支。

| 对象 | 后续实现必须保持的边界 |
|---|---|
| 信息源实例 | 使用稳定 `id` 隔离账号、配置、断点、筛选草稿与任务；`kind` 是实现类型，同类型可有多个实例。名称与图标是显示信息，不能充当路由或权限依据 |
| 来源能力 | 分别声明消息读取、查询、SQL、采集、重放、控制台定时、配置与附件能力。缺失的能力不提供操作入口，操作处理仍检查能力，不能只隐藏按钮 |
| 外部收集器 | 可只发布标准消息；不因此假定能刷新其数据库、用本机 SQL 查询或控制其日程。演示目录中的外部来源用于展示这个区别，未接入真实平台 |
| 渠道类型 | 复用现有管理接口的 `schemas`，由服务提供字段类型、说明和能力；前端提供基础字段控件，不为每个渠道新建页面或独立分发逻辑 |
| 投递目标 | `target.id` 与 `kind` 分开；同类型的不同群、账号或资料库分别配置、投递、回执与恢复，添加目标默认关闭 |
| 渠道能力 | 发送、合成测试、文件上传、操作回写、监听、未知结果恢复分别声明。支持其中一项不自动意味着具备其他能力，也不把所有恢复行为当成飞书行为 |
| 未知描述 | 保留未知来源、目标及未编辑字段；描述暂不可用时只读展示并说明限制，不丢弃配置、不擅自启用或发送。新增字段类型未知时保留原值 |
| 数据与凭据 | 表单只使用经服务白名单投影的安全字段与凭据变量名；实际校验、版本冲突、备份、身份与路径保护仍由现有业务层执行 |

现有实现边界已核对：`messaging/management.py` 已返回目标和字段 schemas，但名称、能力等描述仍需在迁移时补齐；`tools/console/app.py`、`Bridge` 和内置采集配置仍限制微信 / QQ，外部来源当前通过标准事件契约进入处理层。因此本稿证明的是通用 UI 的呈现与交互，不声称现有后台已能直接管理任意来源。后续迁移需要对应调整来源描述与适配边界；不引入任意 Python 动态加载或另造插件系统。

## Pi 完整工作流

“工具活动”改为处理页内的 **Pi 工作流**，沿用参考图的可折叠执行过程：运行摘要在上，事件按时间和序号展开。每个节点先给发生的事情与结果，再按需查看正文；不要求用户先读整段 JSON。

| 节点 | 展示内容 |
|---|---|
| 输入准备 | 实际规则、初始消息、会话与附件短引用；区分模型输入与仅保存在本地的完整来源映射 |
| 每轮请求 | 实际发出的消息上下文与可用工具的安全投影；后续工具历史和新的请求分别记录，不用首轮输入代替整次执行 |
| 模型输出 | 模型实际公开输出的文本、结束或错误状态；不从工具结果或其他轮次补造未记录的输出 |
| 工具调用 | 原始工具名、调用编号、开始 / 等待 / 结束状态、输入参数、返回内容、覆盖范围与错误。渲染不限制为当前三个工具名 |
| 上下文压缩 | 压缩事件、实际保留的摘要与引用；压缩前内容未记录时明确标注，不能假装完整可还原 |
| 失败重试 | 原生重试次数、阶段、原因与等待对象；不把重试提示当作已成功，不重建已完成工具结果 |
| 最终结果 | 提交调用、业务校验与最终保存分别呈现，衔接待办与来源。失败后保留已经发生的上下文和工具结果 |

按运行、批次、回合和 `call_id` 关联，事件有稳定序号，工具输入与返回不串到别的运行。支持正文搜索、按类型筛选、长内容内部滚动、运行完成 / 执行中 / 失败的示例；没有进度百分比或无限旋转动画。

真实实现存在明确缺口：`runtime.mjs` 目前只对部分原生事件输出精简元数据；`collector-extension.mjs` 的 `request_prepared` 只有字符数，未保存完整请求正文；现有测试还特意避免将完整内容混入进度事件。本轮没有改变这些行为。

迁移时保留轻量状态流，完整上下文、模型可见输出与工具正文写入受本机会话权限保护的运行记录，按需分页读取；不能把凭据、认证头、原始密钥或整块图片编码直接塞进事件列表。缺失或被限制的正文显示“未记录 / 内容省略”及实际范围。实时更新保留已展开节点、阅读位置和选中运行，不能每次刷新重绘整页或强制跳到底部。既有最近 200 条事件的响应上限不能冒充完整历史，需接续对应运行记录。

## 现状检查与设计方向

已阅读现有面板截图、`index.html`、`style.css`、`app.js`、`processor.js`、`messaging.js`、`automation.js`，以及控制台和处理层文档。

| 现状 | 本稿的处理 |
|---|---|
| 采集、处理、投递、任务记录连续堆在长页里 | 按使用目标导航；保留原业务顺序，不要求滚动寻找另一模块 |
| 状态卡片上方占据大量空间，结果出现在条件之后 | 顶部用一行概括当前来源；条件、消息和详情并排 |
| 英文眉题、长段说明、默认展开的工具事件争夺注意力 | 中文任务标题；说明靠近相关操作；Pi 工作流成为处理页的次级页签 |
| SQL 注册表需要直接理解完整 JSON | 默认列出文件、启停和用途；编辑仍使用现有注册表形式，不新增规则生成器 |
| 模型“已配置”容易被理解为连接成功 | 明确显示“已配置 · 连接未验证” |
| 投递、完成操作有异步队列与未知结果 | 明确区分提交、等待回写和已确认；未知结果先核对，再考虑重试 |

视觉问题主要是层级和密度，原有绿色体系适合保留。布局重写来自本次用户明确要求；没有按通用营销模板重做品牌。

- 产品：帮助本机使用者检查采集、待办与投递是否按预期工作。
- 气质：克制、准确、有条理。
- 场景：本地消息档案；中性色背景、清楚的分隔线、内容优先。
- 重点：选中消息与其来源、附件状态；不增加装饰图表或未经支持的指标。
- 识别细节：绿色定位线同时用于当前导航和选中消息。

## 从入口走到结果

| 场景 | 用户路径 | 可观察结果与恢复 |
|---|---|---|
| 首次使用 / 已有部署 | 打开面板 → 查看已发现来源 → 预览已有快照 | 无需重复配置已知账号或路径；无配置、无权限、数据库被占用、服务不可达分别解释。自动发现仅为流程示意，未在本稿实现 |
| 日常采集调试 | 采集调试 → 选择平台 → 调整时间 / 规则 → 预览 → 点击消息 | 条件、命中消息与来源保持同屏；搜索无结果不清空输入；修改条件后标注旧结果待更新 |
| 需要最新数据 | 采集调试 → 执行一轮 → 确认正式写入范围 | 成功后才显示断点已更新；不把查询已有快照当成刷新数据库 |
| 历史补录 | 采集调试 → 重放时间段 → 核对范围与已保存规则 | 说明会增加修订 / 附件，不移动定时断点；正式重放保留不受 7 天预览上限限制的行为 |
| 检查 AI 输入 | 待办处理 → 正式增量或指定时间 → 预览上下文 | 本机只读；初始输入与完整本地来源分开；不冒充已读取附件正文 |
| 执行 AI | 预览 → 执行处理 → 确认模型发送范围 → 查看待办 / 工具活动 | 调试输出独立于正式待办；实际请求可能计费；关闭页面不等于取消工作进程 |
| 待办完成 | 行动与材料 → 标记完成 | 先显示等待处理层回写，不把入队当成已完成；原始聊天不变 |
| 投递结果未知 | 投递与回写记录 → 核对目标端 → 确认收到或确认未收到后重试 | 不自动重复发；确认重试说明重复投递的可能性 |
| 失败排查 | 运行记录 → 失败筛选 → 查看任务 | 结果与下一步在前，原始日志折叠；失败或中断后先查实际输出再决定是否重试 |
