# QQ 快照刷新：性能定位与优化

2026-11-15。优化已更新到本机运行目录，正常停止后台服务后重新启动；配置、密钥、筛选断点和已有运行记录保留。只修改采集器内部读取与候选计算，不修改原始 QQ/微信数据库、SQL 规则或消息契约。

## 哪些操作需要改

| 操作 | 判断与实现 |
| --- | --- |
| 内部 B-tree 页变化后比较整棵子树 | 范围过大。改为变化叶页、溢出页所属叶页，以及更新前后叶页归属差异。整表删除、页面释放和复用仍补齐旧行号。 |
| 找到变化溢出页后再次扫描表定位记录 | 重复扫描。与叶页归属在同一次有序遍历中完成。 |
| 按表名集合查询后统一排序 | 查询计划实际产生临时 B-tree。改为逐表有序读取，计划确认无临时排序。 |
| 增长时逐页查询、复制整个私有库 | 对当前 1.30 GiB 私有库产生大量小读取和跨语言调用。改为在已恢复日志的写事务内直接顺序读入镜像，之后仍校验完整预期镜像。 |
| 每轮公开库 `quick_check` 的逐页读取 | 检查保留。使用 SQLite 原生文件映射访问已有页，避免大量显式读取调用；新页、修改页和事务日志仍由 SQLite 管理。 |
| 增加行号或时间索引 | 本次不需要。真实查询计划已使用行号主键和采集器时间索引。 |
| 给 `dbstat.pageno` 添加索引 | 不适用。它是 SQLite 虚拟表，并非可建立普通索引的消息表。 |
| 删除源主库复读、WAL 校验、提交落盘 | 不采用。它们保障并发捕获一致性和失败恢复，不能只因有重复读取就移除。 |

叶页归属数组每页 4 字节，当前每份约 1.3 MiB，只在一次刷新内存活。没有新增轮询、持久缓存、常驻索引或运行时依赖；SQLCipher、SQLite、dbdata 上游源码与原生二进制未改。

## 仍然存在的成本

源文件需稳定复读；`dbstat` 和完整性检查仍遍历相关数据库。公开库文件映射复用系统文件页，不意味着没有物理磁盘读取。数据库增长时，预期镜像仍临时占用约一个私有库大小的内存，当前约 1.30 GiB；本次减少其读取调用，尚未替换镜像校验机制。

最终版本尚未遇到下一轮自然发生变化的真实 QQ 数据，不能承诺有变化整轮的固定耗时。逐阶段计时已保留，后续可直接核对，而无需再次猜测瓶颈。

本地证据在 `.runtime/qq-refresh-research/`：查询计划、固定样本对照、镜像一致性、公开库校验、真实采集及部署校验。证据不含聊天正文或密钥。最终运行文件校验和、配置保留检查、备份位置见其中 `deployment.json`。

## Windows 大库扩容读取修复（2026-11-15）

后续真实运行发现：私有快照超过 1 GiB 时，增长校验镜像的顺序读取会跨过 SQLite 的字节锁区域。Windows 即使对同一进程另开的文件句柄也拒绝这段读取，触发 `category=permission stage=read_previous rollback=complete`；该错误不代表目录缺少权限，旧快照事务已回滚。

修复保留写事务内的大块顺序读取，仅将锁所在页交给同一 SQLite 连接的 `sqlite_dbpage` 读取；SQLite 按自身规则为保留页提供零页。没有释放事务锁、重建整库或跳过校验。镜像构建失败的阶段改为 `resize_image`，避免与旧行候选提取混淆。

回归用例把隔离 QQ 引擎的真实字节锁移到一个小型合成库中，覆盖扩容、缩容、旧行修改、删除、新增与候选合并；旧代码在 Windows 下复现同一权限错误，修复后通过完整性检查和逐行比对。真实账户的一次有变化正式采集也完成：私有库 341404 页，更新 448 页，公开库同步校验通过，规则入库 22 条消息变更；快照刷新约 44.9 秒，其中私有页刷新 14.1 秒、公开库同步 30.7 秒。此为单次运行，不能与前述不同缓存、不同变化量的样本直接比较加速比例。

## 少量变更仍偶发慢读（2026-11-17，issue #29）

基线为 `a4b9708`，Windows x64。一次真实定时采集耗时 190.696 秒，刷新占 171.196 秒；原生页和标准库均为增量，只有 267 个页面写入、1035 条候选。阶段记录表明主要成本并非候选范围扩大：

| 阶段 | 秒 |
| --- | ---: |
| 稳定捕获源库 | 49.533 |
| 更新前候选定位 | 68.802 |
| 增长校验镜像构建 | 7.561 |
| 更新后候选定位 | 1.356 |
| 标准库比较与写入 | 1.291 |
| 标准库校验 | 28.486 |

源库、原生缓存及标准快照位于机械硬盘，密文工作目录位于 SSD。增量仍需复读源库、遍历表页面归属和校验标准库，因此零筛选命中不等于零读取、零源库变更。事后相同已发布快照的只读遍历约 2.2 秒、标准库校验约 0.8 秒，支持磁盘读取与缓存状态放大耗时的判断；没有该轮历史磁盘监控，不能断言具体触发因素。

更新前候选定位改用短暂的只读映射连接。原写连接先持有 `BEGIN IMMEDIATE`，阻止其他 SQLite 写者；只读连接读取同一未修改原生快照，完成后关闭，才开始写页、扩缩容及提交。直接在写连接设置 `mmap_size` 的方案实测没有减少读取调用，不能采用。主库复读、WAL 校验、页面归属算法和完整性校验保持原有要求。

固定合成库 30000 行、153989120 字节，位于机械硬盘；按照正式流程开启主库与页状态库写事务，交错执行旧写连接遍历和新只读映射遍历，结果完全相同：

| 指标 | 原写连接遍历，两轮 | 新只读映射遍历，两轮 |
| --- | --- | --- |
| Windows 进程显式读取调用 | 7524 / 7524 | 3 / 3 |
| 阶段耗时 | 0.1723 / 0.1716 秒 | 0.1601 / 0.1637 秒 |

没有清空系统缓存。这是热缓存、持写事务条件下的候选阶段对照，不是冷读或整轮采集结果；映射缺页的物理读取不计入显式读取调用数。映射不受支持或受引擎上限约束时，SQLite 仍走普通读取。回归覆盖映射读连接只读、其他写者被锁拒绝、写页前连接关闭、扩缩容、失败回滚后重试与逐行一致性。

后台采集成功记录现将阶段耗时、页面数、候选数和增量/基线模式按固定白名单写入每次尝试的 `details.collection`，运行详情可直接查看阶段耗时。路径、账号、未知字段和无效数值不写入这些详情；原结果摘要及历史保留规则不变。刷新间隔内复用快照时，在返回的 `refresh` 中标记 `reused=true`，不把上次刷新耗时重复记作本轮。旧记录和失败前未产生的阶段不推算。

本次未部署到真实采集服务，未验证冷读整轮改善；源库复读、公开库校验和约一份原生库大小的增长镜像成本仍在，不能承诺每轮固定为十几秒。
