# QQ 快照刷新：性能定位与优化

2026-11-15。优化已更新到本机运行目录，正常停止后台服务后重新启动；配置、密钥、筛选断点和已有运行记录保留。只修改采集器内部读取与候选计算，不修改原始 QQ/微信数据库、SQL 规则或消息契约。

## 哪些操作需要改

| 操作 | 判断与实现 |
| --- | --- |
| 内部 B-tree 页变化后比较整棵子树 | 范围过大。改为变化叶页、溢出页所属叶页，以及更新前后叶页归属差异。整表删除、页面释放和复用仍补齐旧行号。 |
| 找到变化溢出页后再次扫描表定位记录 | 重复扫描。与叶页归属在同一次有序遍历中完成。 |
| 按表名集合查询后统一排序 | 查询计划实际产生临时 B-tree。改为逐表有序读取，计划确认无临时排序。 |
| 增长时逐页查询、复制整个私有库 | 对当前 1.30 GiB 私有库产生大量小读取和跨语言调用。改为在已恢复日志的写事务内直接顺序读入镜像，之后仍校验完整预期镜像。 |
| 每轮公开库 `quick_check` 的逐页读取 | 检查保留。使用 SQLite 原生文件映射访问已有页，避免大量显式读取调用；新页、修改页和事务日志仍由 SQLite 管理。 |
| 增加行号或时间索引 | 本次不需要。真实查询计划已使用行号主键和采集器时间索引。 |
| 给 `dbstat.pageno` 添加索引 | 不适用。它是 SQLite 虚拟表，并非可建立普通索引的消息表。 |
| 删除源主库复读、WAL 校验、提交落盘 | 不采用。它们保障并发捕获一致性和失败恢复，不能只因有重复读取就移除。 |

叶页归属数组每页 4 字节，当前每份约 1.3 MiB，只在一次刷新内存活。没有新增轮询、持久缓存、常驻索引或运行时依赖；SQLCipher、SQLite、dbdata 上游源码与原生二进制未改。

## 真实运行暴露的第二个瓶颈

第一版缩小候选范围后的自然定时采集，刷新耗时 **653.410 秒**。这轮没有证明整轮加速，新增阶段计时定位到：

| 阶段 | 秒 |
| --- | ---: |
| 源库稳定捕获 | 56.801 |
| 更新前候选提取 | 2.707 |
| 构建增长校验镜像 | 226.451 |
| 页面写入 | 0.028 |
| 私有镜像完整性检查 | 0.440 |
| 更新后候选提取 | 1.913 |
| 逻辑比较与写入 | 9.662 |
| 公开库完整性检查 | 343.703 |

本轮 238 页更新、825 条候选，最终写入 317 条、删除 56 条。此前一轮为 272 页更新、214737 条候选；数据和系统缓存条件不同，这不是严格 A/B。候选范围已缩小，但逐页读库和公开库校验占了绝大多数时间，因此继续实施大块顺序读取及文件映射。

更新后的真实快照采集验证为**无变化**：刷新内部总计 2.790 秒，包含稳定捕获 2.625 秒，0 页写入、0 行写入。采集服务调用总计 9.460 秒。源捕获逻辑没有改，缓存和无变化条件决定了这次耗时，不能将其与 653 秒的有变化轮次直接比较。

最终代码的采集、页恢复、QQ/微信增量、筛选、调度回归 **145 项通过**；控制台正式采集、只读预览和重放 **5 项通过**。5 个跳过项为平台专属参数组合，不是缺少原生组件。覆盖了旧行修改、删除、溢出页、子树变化、未改写叶页释放、跨表归属、页复用、int64 行号边界、扩容缩容、唯一值交换、未提交 WAL、模式变化及崩溃回滚。

## 仍然存在的成本

源文件需稳定复读；`dbstat` 和完整性检查仍遍历相关数据库。公开库文件映射复用系统文件页，不意味着没有物理磁盘读取。数据库增长时，预期镜像仍临时占用约一个私有库大小的内存，当前约 1.30 GiB；本次减少其读取调用，尚未替换镜像校验机制。

最终版本尚未遇到下一轮自然发生变化的真实 QQ 数据，不能承诺有变化整轮的固定耗时。逐阶段计时已保留，后续可直接核对，而无需再次猜测瓶颈。

本地证据在 `.runtime/qq-refresh-research/`：查询计划、固定样本对照、镜像一致性、公开库校验、真实采集及部署校验。证据不含聊天正文或密钥。最终运行文件校验和、配置保留检查、备份位置见其中 `deployment.json`。
