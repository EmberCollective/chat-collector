# 微信刷新优化与验证

微信继续使用已经提取的上游解密、WAL 合并和 SQLite 校验代码。本次没有改写加密算法，也没有引入 AI、后台子进程或多核工作池。

## 优化方法

### 一个数据库的时间索引只提交一次

原来 `_index_snapshot()` 对每个会话表执行 `CREATE INDEX`，没有显式开启事务。SQLite 会分别提交这些 DDL；大量会话表导致机械硬盘反复同步写入。

现在先 `BEGIN`，创建该数据库全部 `(create_time, local_id)` 索引后统一提交。任一建索引操作失败，关闭连接会回滚本次索引事务，不留下半套新索引。不关闭同步、不跳过索引，也不更改原始数据库。

### 限制详细诊断计算，不限制解密或校验

部分 WCDB 文件存在预分配尾页。本机样本有 3,308 个 HMAC 告警页；原来每页都会计算多种诊断变体、再次解密并写详细日志，尽管最终结果只保留前 8 个样本。

现在仅前 8 个 HMAC 告警页生成详细诊断和逐页日志。每个页的正常 HMAC 检查、AES 解密、页数统计仍然执行，告警总数及最终汇总仍然保留。没有把告警改成通过，也没有删除或跳过告警页。SQLite 完整性校验和失败时保留上次有效快照的行为继续沿用上游实现。

### 暴露分阶段耗时

`refresh()` 返回 `timings_seconds.total`，每个更新数据库的 `validation` 条目还包含 `timings_seconds.decrypt_and_validate` 与 `time_indexes`，单位均为秒。可以从控制台任务结果判断慢在解密校验还是索引写盘。

仍然只刷新源文件或 WAL 指纹变化的数据库；未变化数据库不重新解密。采集消息仍使用原生时间条件 `[上次成功终点, 本轮开始)`，不增加隐式重叠时间窗或 ID 游标。

## 本机测量

2026-11-12，在同一组冻结的 4 个本机数据库副本上测试。包括两个消息库、资源库和 hardlink 库；每次目标为新目录，因此强制全刷新。原始客户端数据只读。

| 场景 | 优化前 | 优化后 |
|---|---:|---:|
| 冻结副本 → D 盘机械硬盘目标 | 59.494 秒 | 4.633 秒 |
| 冻结副本 → C 盘 NVMe 目标 | 3.275 秒 | 0.887 秒 |
| 无变化刷新检查 | 约 0.002 秒 | 约 0.002 秒 |

D 盘旧实现的索引阶段占 57.816 秒，说明主要瓶颈是逐索引提交，不是需要更多 CPU 核心。以上是带性能采样的单次测量，受磁盘缓存和其他负载影响，不应当作为持续性能保证。

随后直接读取正在使用的原始源目录、写入独立 D 盘测试目录，全刷新耗时 **1.543 秒**，4 个库均通过 `quick_check`。这是数据库刷新耗时，不包含消息规则筛选、附件归档和批次输出，也未改动正式调度、断点或配置。

## 正确性与开发验证

- 优化前后逐库比较全部表数据和 SQLite schema，共 **53,743 行**完全一致；4 个库均通过 `quick_check`。
- HMAC 告警计数保持 535、655、2,118、0，未被掩盖。
- 回归测试覆盖时间范围、消息文本、文件和 @所有人解析、未变化快照复用、源变化后的刷新，以及压缩内容上限。
- 新增测试：后续表建索引失败时前面创建的索引回滚；原生 SQLCipher 生成的样本追加 12 个尾页后仍检查和解密所有页，但详细诊断只生成 8 个样本。

运行微信专项测试：

```powershell
$env:PYTHONPATH = "$PWD/runtime-deps"
python -m pytest tests/test_wechat.py tests/test_wechat_followup.py -q
```

修改微信刷新时，优先查看 `collector/adapters/wechat.py` 的刷新编排，再查看 `collector/vendor/wechat/decrypt.py` 的保留上游实现。上游来源及本地修订记录在 `collector/vendor/wechat/UPSTREAM.md`。排查性能应先看分阶段耗时，再使用只读源副本重复测量；不要为测试清空正式 manifest、快照或断点。

## 边界

本次没有实现多进程解密、页级增量解密或跨库全局事务。文件变化后仍完整处理该数据库；大库的 CPU、内存与磁盘成本仍会随体积增长。每库完整性检查不等于多个数据库处于同一全局时刻。后到的旧时间戳消息仍需要显式时间段重放。
