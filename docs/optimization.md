# 采集性能与数据完整性

优化顺序是先分段计时，再减少重复工作，最后考虑并行。采集层仍使用原生数据库实现和确定性代码，不调用 AI。

## QQ：先处理磁盘瓶颈

本机有 16 个物理核、32 个逻辑核，但 D 盘为 SATA 机械硬盘，C 盘为 NVMe SSD。QQ 加密数据库约 1.34 GB，每次源库或 WAL 变化都会生成完整明文快照。增加 Python 进程不能消除这次完整写入，并可能增加同一机械硬盘上的竞争。

已实施：

1. 用 SQL `changes()` 获取刚复制的行数，与明文目标表行数核对，避免再次完整读取并解密源表。仍保留所有表、原始 rowid、序列、索引、视图和触发器。
2. 支持 `source.work_dir`，在 SSD 上生成稳定的 DB/WAL 副本、解密、重建索引并执行完整性检查。未配置时沿用明文目录所在磁盘。
3. 跨盘发布先写正式目录中的临时文件，刷新到磁盘并核对 SHA-256，再原子替换上一份快照。复制失败或哈希不符时保留旧快照；源标记也支持跨盘发布。标记未更新只会导致重试，不会把未完成的刷新记为成功。
4. 附件只先建立文件名目录，对实际匹配项再解析路径并验证允许目录，避免遍历时对大量无关文件进行昂贵的路径解析。归档仍保留路径授权、大小及哈希校验。
5. 刷新结果提供 `timings_seconds`：capture、export、integrity_check、time_indexes、publish、total。未变化时直接复用快照。

在 `config/qq.toml` 已有 `[source]` 中配置：

```toml
work_dir = 'C:\Users\Administrator\AppData\Local\Temp\chat-collector-qq'
```

选择本机 SSD 的目录即可，不应指向 QQ 原始数据库目录。CLI 和可选调试台读取同一配置；正式解密库、批次和附件路径分别由原有配置决定。

临时空间约需加密副本、明文库及索引/事务日志的总和，当前数据库建议至少预留 4 GB。成功或异常返回时自动清理本轮临时目录；强行结束进程或断电可能遗留临时文件，确认没有采集任务运行后才可清理 `qq-refresh-*`。临时目录包含明文聊天内容，应使用当前用户私有目录，不应同步或共享。D 盘发布时仍需容纳旧快照与新快照。

## 测量结果与边界

2026-11-12 本机实测：

| 对比 | 优化前 | 优化后 | 说明 |
|---|---:|---:|---|
| QQ 实际一轮采集 | 50.411 秒 | 31.182 秒 | 原目录对比 SSD 工作目录；两轮分别命中 109、125 条，不是完全相同输入 |
| QQ 后续实际采集复测 | — | 25.100 秒 | 命中 229 条；说明实际耗时受缓存与负载影响 |
| 其中数据库导出 | 41.518 秒 | 10.857 秒 | SSD 临时目录减少机械盘随机写入 |
| SSD 方案跨盘发布 | — | 12.643 秒 | 包括写回正式 D 盘、落盘及校验 |
| 同一固定快照原生导出 | 12.205 秒 | 10.816 秒 | 仅取消重复源表计数，均在 SSD 上 |
| 相同 78 条消息附件处理 | 8.397 秒 | 0.757 秒 | 7 个附件，减少无关路径解析 |

分段实验不能相加后冒充实际一轮耗时。实际速度会随磁盘负载、缓存、消息量和附件量变化。固定快照核对了 1,573,185 行，全部行及 schema/index 定义一致。

测试了 SQLCipher 原生 4 工作线程，固定快照导出约 10.415 秒，相比只消除重复读取的 10.816 秒收益有限，因此没有默认启用多进程或增加占用。加密到明文的 SQLite backup 实验不受当前引擎支持，没有替换生产导出路径。

当前仍是完整快照刷新，不是数据库页级增量解密。若以后完整写入成为不可接受的瓶颈，可评估直接在稳定的加密副本上用原生 SQLCipher 查询时间窗；这会改变明文快照的交付方式，应独立验证，不能直接省略历史表或完整性校验。

微信的测量与实现见 [微信性能](wechat-performance.md)。
