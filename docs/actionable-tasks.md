# 面向执行的待办

处理层负责说明“要做什么、怎么做、依据是什么”，消息层负责材料交付、外部同步和提醒。采集层和 SQL 筛选不参与优先级判断。

| 字段 | 要求 |
| --- | --- |
| `title` | 动作和对象，如“填写并提交申请表” |
| `event` | 成果、明确的接收人、提交入口或验收要求；不确定的要求不能写成事实 |
| `action_steps` | 按执行顺序排列的字符串数组，仅含原文有依据的步骤；最多 50 项，每项最多 2000 字符 |
| `time`、`people`、`location` | `people` 为有依据需要参与事项的人，角色可为参与人、提交人、审批人等；仅明确指派时才写负责人。其他字段未知值保留 `null` 或空数组 |
| `sources`、`attachment_evidence` | 程序映射的消息和已读附件证据，供核查和整理材料 |
| `material_refs` → `materials` | 模型选择所需附件短编号；程序映射成消息与附件序号以及原始或已解析附件元数据 |
| `needs_review`、`review_reasons` | 执行时具体缺什么，不能只写“待确认” |

`action_steps` 是可选的兼容扩展。旧响应没有该字段时规范化为 `[]`；空白步骤、错误类型、过长内容在 Pi 接受提交前被拒绝，模型可按反馈修正。提交映射、持久化和任务事件输出均保留步骤；查重工具及当前上下文中的已有任务也返回步骤，供后续更新时保留有效要求。没有另建模型循环。

一条任务内的步骤不等于多条独立任务。只有需要独立跟进的交付物、参与范围或期限才拆分。步骤中的链接、材料名称和填写要求必须来自消息或已经读到的附件内容，不能猜测。模型不生成归档路径和下载地址。

执行材料用 `material_refs:["f1"]` 选择，最多 100 个引用；必须来自本任务已引用的消息，不能从别的会话偷带文件。程序将它们映射为 `materials:[{message_key,attachment_index,attachment}]`，已读且被 `sources` 引用的证据也自动并入。模型自填的 `materials` 会被丢弃重建；原始路径和附件身份来自可信本地映射。更新同一任务时，按消息与附件序号合并历史材料。消息层只交付这个清单及附件证据，**不能把来源消息的所有附件都当成与任务有关**。旧任务只有消息附件但无明确关联时，保留需确认状态，不自动外传。

选择材料并不表示读过内容；未读原件也可作为待填写模板交付，材料缺失则保留缺失状态。`material_refs` 是当轮短引用，不进入持久化任务；持久化的 `materials` 才是消息层使用的关联清单。

最终提交通过全部校验后，程序为选中的材料调用提供方的准备接口：优先复用通过路径和哈希校验的归档，否则按原消息定位并归档、解码。预提交校验不会执行这项准备；未选中材料不触发定位。此过程不解析正文、不生成已读证据、不向模型追加内容，也不触发整轮数据库解密。准备失败时保留 `status=unavailable` 和原因，不中断其他待办输出。

附件仍按需读取，不要求读完全部文件。已知消息足以支撑的任务可先提交；依赖尚未读取的材料作判断时必须标记复核。新提交的来源保持单会话；跨平台同一事项通过 `find_related_tasks` 复用已存在的任务 ID，旧来源由程序合并保留。

默认规则位于 `processing-rules/default.md`，可自行修改。**规则内容参与分组指纹，修改后既有分组可能重新进入待处理队列并产生模型费用**；本轮没有自动调用真实模型重处理历史内容。优先级按原消息的时间和证据判断；到期与提醒安排交由消息层处理。
