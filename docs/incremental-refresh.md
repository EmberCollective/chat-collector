# 微信与 QQ 增量刷新

收集层保留已验证的明文库，根据实际变化的数据库页更新。第一次建立基线需要完整读取和解密；后续不按消息时间猜测变化，也不重新导出整个数据库。SQL 规则、消息契约、人物资料、附件接口和处理层输入格式不变。

## 配置和运行

两个平台的配置文件均已启用：

```toml
[source]
snapshot_mode = "incremental"
```

扫描间隔仍使用 `schedule.interval_seconds`，刷新间隔仍使用 `schedule.refresh_interval_seconds`，没有新增固定间隔。缺省 `snapshot_mode` 的旧配置沿用 `full`。切回 `full` 可使用原完整导出路径；再次启用增量时若明文布局发生改变，会重新建立基线。

本机原生组件位于 `runtime-deps/native/`，不提交二进制。迁移机器后先构建：

```powershell
python tools/build_sqlcipher_pages.py --toolchain C:/Strawberry/c
```

构建需要 Windows x64、GCC/MinGW 和 OpenSSL 开发文件；本机使用 Strawberry 自带工具链。脚本校验固定源码归档的 SHA-256，编译未修改的 SQLCipher/SQLite 源码，保存来源与编译参数，并复制 OpenSSL 运行库。缺少组件时明确报错，不自动下载、不悄悄每轮改为完整导出。

## 共同刷新流程

1. 在原有采集锁内读取原数据库及 WAL 的固定前缀。主库复读比较、文件身份检查、WAL 前缀复查及回滚日志检查通过后，才接受快照。源文件始终只读；持续变动时最多重试三次，失败保留旧明文库和采集断点。
2. 私有密文镜像按 4096 字节页比较，只写变化页。沿用已有 WAL 校验代码，仅采用校验通过且已经提交的事务；未提交尾部不发布。
3. 原生 SQLCipher 读取解密页，以有效主库页加已提交 WAL 页的 SHA-256 判断变化。指纹与消息时间无关，因此旧消息修改、删除、索引变化及页复用也会被发现。
4. 明文页和对应指纹放入同一个 SQLite 多库事务，使用 DELETE 回滚日志及 FULL 同步。校验通过才提交；异常回滚两者。进程意外退出后由 SQLite 恢复日志。
5. 无变化时不写明文页。源身份、密钥配置、明文目标标记异常或首次迁移时建立新基线，先校验临时库，再替换旧库。外部修改目标会触发重建，不把它当作可信缓存。

指纹比较仍需顺序读取原始主库；这是减少解密和写入，不是消除所有全库读取。数据库大小变化时，使用原生反序列化接口在内存中校验预期页面，避免额外写一份完整临时库。内存开销约增加一个原生明文库的大小；内存不足会失败并回滚。

QQ 的 WAL 可能预分配空间：即使主库未变，尚未提交的尾部也持续改写。捕获先确定最后有效提交边界，只复制、复查这个前缀，避免把正常追加误报为不稳定；WAL 头、已提交帧、主库的变化仍需重试。私有镜像也不反复写入这些未提交尾部。

## 微信：直接更新明文页

编号消息库、联系人库及已配置的资源库分别刷新。保留源库原有页布局和索引，不再向页对齐的明文库插入采集器专用索引。规则 SQL 原样查询，因此没有时间索引的旧表仍可能扫描较多记录。

此次 `message_1.db` 的失败原因是：逻辑页数为 1933，物理文件/WAL 提交尺寸为 2560，尾部 627 页是全零预分配空间。旧逻辑将物理页数写进明文头，完整性检查遂报告 `Page …: never used`。现在只在页头计数有效、尾部已证明全部为零时排除预分配尾部；非零页或无效计数不截断。首次和后续变化刷新仍执行完整 `integrity_check`。

各微信数据库独立事务，不声称所有数据库来自同一个全局时刻。一库失败会终止本轮采集和断点推进，已发布批次仍可处理。

## QQ：原生页缓存加标准 SQLite 行同步

QQ 的文件有 1024 字节外层头。超过 1 GiB 后，其锁保留页位于第 262144 页，标准 SQLite 位于第 262145 页。真实库的 262145 页包含有效索引数据，因此不能直接把解密页作为标准 SQLite 发布。

收集层内部维护两种明文表示：

- 私有原生页缓存：使用独立 SQLCipher DLL，在打开连接前调用 SQLite 官方 `SQLITE_TESTCTRL_PENDING_BYTE`，匹配 QQ 保留页位置。默认引擎的全局设置不受影响。
- 对外标准 SQLite：仍在原来的 `decrypted/nt_msg.db`，原有筛选和身份补全代码正常读取。

SQLite 官方 `dbstat`、`sqlite_dbdata`、`sqlite_dbptr` 提供页面归属和行号：变化叶页选出相关行，溢出页找到所属记录，变化内部页保守包含整个子树。更新前后的行号取并集，包含已删除或被复用的页，避免遗漏旧消息和删除。没有新增自写 B-tree 或密码算法。

对外同步仅比较候选行，删除旧版本再插入新版本，以支持唯一值交换；保持 rowid、列类型、BLOB、自增序列、索引、视图、触发器及版本字段。复制期间不重放业务触发器。没有变化的记录不重写。

QQ 的标准公开库保留原采集器的时间索引，避免刷新变快后筛选反而退化为全表扫描；这些附加索引不写入原生页缓存。

候选仅在“上次成功发布所对应的原生缓存版本”与本轮更新前版本完全相符时使用。原生页已更新但对外同步失败时，公开库保持原状；下一轮退回完整逻辑对比，不能拿空候选跳过漏掉的变化。模式变化或公开库损坏采用校验后的临时重建；不支持的虚拟表明确失败。

QQ 首次基线执行完整 `integrity_check`。后续原生缓存和公开库执行 `quick_check` 结构检查；公开库索引由标准 SQLite 的事务写入维护，不在每轮重复完整索引逐行比对。返回值的 `validation` 标明实际检查方式。

## 文件与恢复

| 内容 | 位置与生命周期 |
|---|---|
| 对外明文库 | 原 `source.decrypted_dir`，路径不变 |
| 页指纹、配置摘要和基线标记 | 明文目标同级 `.incremental/<库名>/` |
| 密文镜像 | `source.work_dir/pages-<平台>-<源路径摘要>/`；未配置则在对应私有目录 |
| QQ 原生明文缓存 | `decrypted/.incremental/qq-native.db`，只供收集层使用 |
| QQ 发布版本标记 | `decrypted/nt_msg.logical.json`，不含密钥 |
| 暂存文件 | 各目标专属私有目录，正常结束删除，下一次持锁运行清理崩溃遗留暂存 |

稳定运行约保留一份密文镜像；QQ 另保留一份原生明文缓存。QQ 当前规模两者合计约额外 2.7 GB，首次重建还需要临时库和事务日志空间。后续主要写变化页和日志，不随扫描轮次累积完整副本。删除缓存后下一轮必须重建，不要删除对外库、采集状态库或附件归档。

密文镜像、明文缓存、附件及导出均留在本机；明文目录应保持私有。原始微信、QQ 文件从不修改。文件标记不是对抗恶意篡改的安全签名；运行中的明文库不应交给外部程序写入。

## 已验证的边界与实测

回归覆盖旧行修改、删除、新增、WAL 未提交事务、扩容、VACUUM 缩小、模式变化、损坏密文、外部改写明文、故障回滚以及子进程强制退出恢复；QQ 另覆盖溢出页、内部页子树、候选版本失配、唯一值交换和标准库兼容。

2026-11-13 本机真实库记录（只计算数据库刷新，不含附件和模型处理）：

| 场景 | 耗时 | 实际写入 |
|---|---:|---|
| 微信 5 库有变化一轮 | 2.403 秒 | 7 个明文页 |
| 微信随后无变化一轮 | 0.737 秒 | 0 个明文页 |
| QQ 正常增量一轮 | 10.488 秒 | 72 个原生页；49 条插入/新版本、27 条旧版本删除 |
| QQ 调试台正式采集复测 | 数据库刷新 9.876 秒 | 60 个原生页；59 条插入/新版本、27 条旧版本删除 |
| QQ 无变化一轮（前一轮实测） | 2.729 秒 | 0 页、0 行 |

QQ 该轮从约 158 万行中选出 1673 条候选进行逻辑比较；49 条包含更新后的版本，不等同于49条新消息。旧完整路径历史实测约25–31秒，输入及磁盘负载不同，不能视为同输入基准。首次迁移、模式变化或缓存失效仍会慢；不承诺每轮固定耗时。

另一轮内部页发生变化，保守候选范围扩大到 181326 行，刷新为 17.501 秒。增量按实际页变化工作，整棵子树变化或大量历史改写的成本会更高。

## 处理与采集独立

正式处理只读已发布的 JSONL，调试处理只读已验证的明文快照。旧 `input.refresh_collectors` 开关停用并提示迁移；需要最新数据时先运行采集。数据库刷新失败不会触发模型调用，也不再阻止已有批次生成待办。这是对先前故障耦合的独立修复，不改变处理层契约或 SQL 规则。

## 原生来源

- SQLCipher 来源：[sqlcipher3 0.6.5 源码归档](https://pypi.org/project/sqlcipher3/0.6.5/)，归档 SHA-256：`368a77f1bc8f6a5b88a7b0774bcf681dc8127511948727a359223629efd9d634`。包含 SQLCipher 4.20.0、SQLite 3.54.1；启用上游 DBPAGE/DBSTAT 编译选项，源码未改。
- 行数据扩展：[SQLite 3.51.0 源码归档](https://www.sqlite.org/2025/sqlite-src-3510000.zip)，归档 SHA-256：`5330719b8b80bf563991ff7a373052943f5357aae76cd1f3367eab845d3a75b7`；直接编译 `ext/recover/dbdata.c`。扩展必须显式链接独立 QQ DLL，不能把一个引擎的连接指针传给另一个引擎。
- 依据：[SQLite DBPAGE](https://www.sqlite.org/dbpage.html)、[DBSTAT](https://www.sqlite.org/dbstat.html)、[WAL 格式](https://www.sqlite.org/fileformat2.html#walformat)、[多库原子提交](https://www.sqlite.org/atomiccommit.html)。

构建目录保留上游源文件及版权头，运行库遵循各自上游许可。组件只用于本地读取和快照更新，没有安装替代反编译引擎。
