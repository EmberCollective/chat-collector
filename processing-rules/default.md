# 待办提取规则

只提取消息中有依据、需要有人执行的事项。普通闲聊、广告、没有行动要求的转发，不生成待办。目标是让用户读完待办就知道下一步怎么做；信息不足时写清具体缺口，不用猜测填满字段。

## 优先级

| 级别 | 判断依据 |
| --- | --- |
| P0 | 明确的紧急事故、阻塞事项，或必须立即行动且延误后果严重。 |
| P1 | 明确重要，并在原消息当天或此后 24 小时内到期；需要尽快安排。 |
| P2 | 有明确责任和要求的常规任务，已有期限但并非紧急。 |
| P3 | 可以安排到后续日程的事项，没有紧迫期限。 |
| P4 | 有行动依据的低优先级可选事项，或重要性与期限尚待确认的事项。 |

结合重要性、明确期限和后果判断，不因单个“紧急”词就定为 P0。以对应原消息的发送时间理解“今天”和紧迫程度，不因模型调用延迟擅自升级；后续提醒频率由消息层配置。提供具体的 `priority_reason`。优先级依据不足时用 P4 并简要备注依据缺口；仅缺参与人员姓名等字段，不抹去已经明确的紧急后果。连行动要求都不成立时不创建任务。

## 用户应该怎么做

1. `title` 用“动作 + 对象”，例如“填写并提交奖学金申请表”；不只写“重要通知”“奖学金事项”。
2. `event` 简洁说明目标、需要提交的成果，以及正文明确的接收人、提交入口或验收要求。将已经确认的要求与需要核实的内容分开，不用大段聊天代替说明。
3. `action_steps` 按实际执行顺序列出有依据的步骤。一步能完成就写一步；不知道具体操作时用空数组，不补造流程、资格条件、材料、审批或验收标准。不得把“阅读全部附件”“回群确认”当作所有任务的默认步骤。
4. 需要表格、PDF、图片或其他材料时，写清原始材料名称及其用途；只有阅读了对应内容，才能据此写出填写要求。明确给出的报名、上传或会议链接可直接保留原链接，不拼接网址、不替换成猜测的官网。
5. 用 `material_refs` 明确选择执行本任务所需的附件索引，例如 `["f1"]`；附件所属消息须在本任务 `sources` 中引用。同条消息中的其他文件不自动交付。可以选择未读材料，但选择不代表其内容已核实；已读并作为 `sources` 引用的附件也会自动关联。附件归档、资源编号、下载入口和来源跳转由程序补齐，不生成文件路径、hash 或下载地址。附件缺失、未读或无法解码时如实说明；仍能从消息确定的步骤可以输出。
6. `action_steps` 是同一任务内的步骤。独立的交付物、参与范围或期限需要分别跟进时，拆成多项待办；不要为每一个简单动作机械新建任务。

## 时间、人物、地点和事件

- 一条消息可以包含多项待办；同一会话中的多条消息也可以共同描述一个事项。参与人员、开始时间、截止时间、地点分别输出；未知项为 `null` 或空数组。
- “明天”“下周一”等相对时间以对应原消息的发送时间和配置时区为基准，不使用模型调用时间。无法唯一确定日期时保留原话，时间字段留空并简要备注依据缺口。只给日期时保留日期，不擅自补成某个钟点。
- `people` 表示有依据需要参与本事项的人，不是负责人名单。区分发信人、参与人、提交人、审批人及被通知人；`role` 按正文确定，只有明确指派负责时才写“负责人”。有参与人但没有负责人不属于人员缺失。没有正文依据时，不把发信人或被通知人自动加入，也不把群通知默认当成当前用户必须完成的任务。需要报名、申请等自愿行为时保留其可选性质。
- 没有提及地点时留空；线上地点只保留正文明确给出的会议室、平台或链接描述。

## 上下文、查重和修订

- 同会话内时间相邻的消息可以联合理解；这些是筛选后的候选消息，未必覆盖原会话全部内容，不推断缺失部分。历史上下文只辅助理解，新任务必须由本段主体消息提供依据。
- 新建前用 `find_related_tasks` 搜索完整待办库，按平台、会话、关键词、关联人物、时间、优先级和状态组合筛选。结果有 `has_more` 时继续分页或缩小范围；没看完结果不能断言不存在。
- 同一事项的补充、改期、取消复用查询返回的 `task_id`。可查找跨平台的同一事项，但本次提交的每条任务只能引用一个会话的新证据；已有任务的旧来源由程序保留。不同事项即使措辞或人名相同也不强行合并，周期性重复事项不当作上一期的修改。
- 更新已有任务时保留仍有效的要求和步骤，只修改有新依据的部分。明确取消时标记 `cancelled`；模糊否定或转述只备注存在歧义，不擅自取消。不把“收到”“好的”当作完成证明。
- `sources` 保留支撑本次判断的消息短引用，如 `m1`，或实际读取过的附件证据，如 `f1:p2`；不能引用输入里没有或尚未读取的证据。
- 附件初始仅有索引。相关时用 `read_attachment(ref="f1")`，由工具自动定位、归档、解码和读取，无需路径。只读取判断任务所需的内容，允许跳过无关附件；部分阅读不代表整份材料已经核实。

## 输出要求

使用系统和 Pi 原生 `submit_tasks` 工具的 JSON 结构。没有待办时提交 `{"tasks": []}`，不返回裸数组。允许根据已检查内容返回空待办，不要求读完全部附件；可用 `attachment_decisions` 的 `ref`、`reason` 说明跳过理由。

每项任务提供 `priority_reason`；所有有依据的待办默认直接入库，无人工校验环节；`needs_review` 固定为 `false`。在可选 `notes` 中简述影响执行的信息缺口，兼容字段 `review_reasons` 留空。不要仅因人员或截止时间为空机械追加说明，也不要反复提示“待核对”。`action_steps` 最多 50 项，每项不超过 2000 字符，保持简洁。

以下仅为字段示例，实际引用、日期、姓名、材料和链接必须来自本轮资料：

```json
{
  "tasks": [{
    "task_id": null,
    "title": "填写并提交申请表",
    "event": "填写通知附带的申请表；提交期限及接收人尚未给出。",
    "action_steps": ["填写通知附带的申请表"],
    "material_refs": ["f1"],
    "priority": "P4",
    "priority_reason": "有明确行动要求，但尚无重要性或期限依据。",
    "status": "open",
    "time": {"start": null, "deadline": null, "text": null},
    "people": [],
    "location": null,
    "needs_review": false,
    "notes": ["通知未提供具体提交入口。"],
    "review_reasons": [],
    "sources": ["m1"]
  }]
}
```
