# 待办提取规则

此文件是可修改的本地处理规则。只提取消息中有依据、需要有人执行的事项；普通闲聊、广告、没有行动要求的转发，不生成待办。

## 优先级

- **P0**：明确的紧急事故、阻塞事项，或必须立即行动且延误后果严重。
- **P1**：明确重要，并在今天或 24 小时内到期；需要尽快安排。
- **P2**：有明确责任和要求的常规任务，已有期限但并非紧急。
- **P3**：可以安排到后续日程的事项，没有紧迫期限。
- **P4**：低优先级的可选行动、建议或待确认事项。

优先级来自事项的重要性、明确期限和本规则，不因为消息含有“紧急”等单个词就自动定为 P0。证据不足时用 P4，并标记需要人工复核。不要把所有消息都变成任务。

## 时间、人物、地点和事件

1. 一条消息可以包含多项待办；多个连续消息也可以共同描述同一事项。
2. 每项任务写清动作与对象。负责人、参与人、开始时间、截止时间、地点分别输出；未知项为 null 或空数组，不补造。
3. “明天”“下周一”等相对时间以对应原消息的发送时间和配置时区为基准，不使用模型调用时间。无法唯一确定日期时保留原话，时间字段留空并标记复核。
4. 区分发信人、任务负责人和被通知人。没有明确指派时，不把发信人自动当作负责人。
5. 没有提及地点时留空；线上地点只保留正文明确给出的会议室、平台或链接描述。

## 上下文和修订

- 同会话内时间相邻的消息可以联合理解；它们是筛选后的候选消息，未必覆盖原会话的所有消息，不推断缺失内容。
- 历史上下文只辅助理解，不再次提取纯历史任务；新任务必须由本段主体消息提供依据。
- 新建前用 find_related_tasks 搜索完整待办库，可按平台、会话、关键词、关联人物、时间、优先级和状态组合筛选；结果有 has_more 时继续分页或缩小范围。同一个事项的补充、改期、取消应复用查询返回的 task_id，可关联跨平台的同一事项。不同事项即使措辞或人名相同，也不要强行合并。
- 明确取消的事项标记 cancelled；模糊的否定或转述应标记复核，不擅自取消。
- 保留所有支撑本次判断的 sources 短引用（例如 m1、实际读取过的 f1:p2），不能引用输入里没有或尚未读取的证据。附件初始仅有索引，相关时用 read_attachment(ref="f1") 自动定位、归档、解码和读取；不需要提供路径。只读取任务所需内容，允许跳过无关附件；不能假装已经阅读未读取的内容。

## 输出要求

按系统和 Pi 原生 submit_tasks 工具提供的 JSON 结构提交 tasks。没有待办时提交 {"tasks": []}，不返回裸数组；允许根据已检查内容返回空待办；不要求读完全部附件，不把未读或缺失内容声称为已核实。可用 attachment_decisions 的 ref、reason 说明跳过理由。为每项任务提供 priority_reason；不确定的任务设置 needs_review=true，并在 review_reasons 说明具体缺口。
